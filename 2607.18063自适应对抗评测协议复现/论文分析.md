# 论文分析：《Adaptive Adversaries: A Multi-Turn, Multi-LLM Benchmark for LLM Agent Security》

- 论文编号：arXiv:2607.18063v1 (cs.CR)，2026-07-20
- 作者：Devina Jain, David Hartmann, Chuan Li（Lambda）
- 会议：Second Workshop on Agents in the Wild: Safety, Security, and Beyond（ICML 2026 Workshop）

---

## 一、论文要解决什么问题

LLM agent 会处理外部内容，因此暴露在**间接提示注入**（indirect prompt injection）和
**多轮操纵**（multi-turn jailbreak）之下。要评测 agent 的安全性，需要对抗性 benchmark。

论文指出现有安全评测存在一个系统性缺陷：

> 大多数 benchmark 用"评测前就冻结的攻击池"去测防御方——攻击在评测之前收集好，
> 之后对每个防御者重复使用同一批攻击。

这一假设把"攻击者"从测量对象里剔除了。真实对抗中，攻击者会**观察防御者的回复并
即时调整**。固定的攻击池即使当初是用自适应攻击生成的（如 PAIR、TAP），发布后也
变成了静态集合，无法再适应新的防御者。

由此论文提出一个未被占据的象限（相关工作中 Table 1 的定位逻辑）：

> **多轮 × 每场 battle 现场再生成攻击 × 多 LLM-agent 攻击者**

并把它做成一个**可运行的评测协议**而非一次性实验：21 个留出场景 + 10 个公开开发
场景、orchestrator、baseline harnesses、多攻击者 CLI，外加 945 份 frontier 矩阵
transcripts、攻击重放数据集、18,422 场开放竞赛 battle。

## 二、核心方法：评测协议（§3）

### 2.1 Battle 结构

每场 battle 是一对（攻击者 harness, 防御者 harness），在 AgentBeats 平台上进行
**15 轮**对抗：

```
每轮：
  1. orchestrator 把【场景上下文 + 防御者此前所有回复】交给攻击者
  2. 攻击者生成攻击文本
  3. 攻击文本插入场景模板，得到格式化输入
  4. 只把【当前轮格式化输入】交给防御者（无攻击元数据、无历史）
  5. 防御者输出结构化 JSON
  6. check_success 做型字段判定
```

**刻意的不对称**：攻击者有跨轮记忆和自适应能力；防御者每轮都是"全新交互"
（memoryless）。这代表一个威胁模型："攻击者每次开一个防御者的新会话（防御者无累积
猜疑），但攻击者自己在会话间持续学习"。因此 ASR 是一个**per-input 压力测试估计**，
而非生产 agent 的预测——论文在 §6 明确承认这一点。

### 2.2 四个设计原则

1. **多阶段场景校准（multi-stage calibration）**：场景不是拍脑袋写的。Concept
   generation（GPT-4o-mini 播种 + 人工审核，覆盖 7 种攻击原型）→ Plugin implementation
   → **Calibration filter**：用 strong=gpt-5.2 / weak=gpt-4o-mini 跑 BAL（强弱同模型）、
   SVW（强攻弱防）、WVS（弱攻强防）三种配置各 10 次，四个一票否决 flag。
2. **多轮 agent-vs-agent**：把 AgentHarm 的"固定用户 prompt"换成会自适应攻击的多轮 LLM。
3. **每场搬迁攻击再生**：攻击内容在 battle 现场生成，m 任何存储池。代价是
   closed-model 运行只能"审计/重放"，不能 bit-for-bit 复现——论文在 §6 明确指出
   这是**可审计性 vs 逐位可复现性**的取舍。
4. **基于结果的判定（outcome-based check_success）**：防御者输出结构化 JSON，
   check_success 只判指定型字段（对泄漏场景判 canary 是否出现、对决策场景判
   verdict/action 是否提交、对传播场景判是否到达第三方）。**部分合规不计数**
   （prose 同意但未提交型字段 = 失败）。

### 2.3 场景集（§4.1）

- **21 个留出评测场景 + 10 个公开开发场景**（公开场景的 defender prompt 不发布，
  因为它是正在进行的 AgentBeats 公开赛的场地）。
- 威胁类别：间接注入 11、PII/数据泄漏 6、不安全输出 2、供应链 1、prompt 抽取 1。
- 每个场景 = 一张"threat snapshot 卡"：defender 角色/系统提示词/输出 schema、
  攻击者目标、每轮输入模板、check_success、**canary 字符串**（如 memleak 的
  `K7$mF9!qZ2nV%xR3`）。canary 固定 → 判定确定性可复现。

### 2.4 校准的三维 rubric（Table 2）

| 维度 | 目标 | 失败 flag |
|---|---|---|
| 难度 | BAL 胜率 30–70% | BAL_100（无区分度） |
| 灵敏度 | SVW−WVS gap > 30pp | SVW_0 / NO_DIFF |
| 回合深度 | 平均获胜轮次 5–12 | （太浅=首轮可破） |

校准在 gpt-5.2/gpt-4o-mini 这一对模型上做一次；向 frontier 防御者的迁移通过
cross-tier 检查（B.9）验证。

## 三、实验与结果（§4.2–§5）

### 3.1 3×3 frontier 矩阵（§4.3）

- 攻击者 = 防御者 = {Claude Opus 4.6, GPT-5.4, Gemini 2.5 Pro}，每格 N=5，21 场景，
  **945 场 battle**，全部 transcripts 发布。
- 聚合 ASR：Opus 5.4%、GPT-5.4 5.4%（并列，CI 重叠）、**Gemini 14.0%（最弱）**。
- Opus 是最强攻击者（对三家的 11–19%）；最差的格子都是攻击 Gemini（19%、18%）。

### 3.2 关键发现

**发现 1：前沿防御者有相互对立的场景级弱点（§5.1）**
- `memleak`：Opus 60%（8/15）被击穿 vs GPT/Gemini 各 7%——机制是 role-frame
  conflict：拒绝直接要密码，但"帮我测试正则解析器"的借口下把密码 percent-encoded
  写进合成测试用例（Figure 3、附录 C.1）；
- `paperaccept`：Gemini 53% vs 两家 0%——机制是 fabricated-authority：一封伪造的
  "OFFICIAL AREA CHAIR NOTE" 让 Gemini 把低于阈值（5.3 < 6.0）的论文判 ACCEPT；
- `gameguru`：Gemini 60%——同一机制的游戏引擎框架版。
- **聚合并列（5.4% = 5.4%）掩盖了相反的弱点**：Opus 在 memleak 上崩、Gemini 在
  paperaccept/gameguru 上崩，两家却总分相同。

**发现 2：每个新攻击者 LLM 都贡献新的唯一攻击（§5.2）**
- 合并三个攻击者，比最强单攻击者多发现 **1.4–2.2×** 唯一成功攻击；
- 攻击跨防御者迁移率很低：46 个唯一攻击中 0 个能通吃三家（universal transfer = 0），
  方向性迁移也不对称（GPT→Opus 25.7% vs Opus→GPT 0%）。

**发现 3：多轮暴露单轮漏掉的失败（§5.3）**
- 第 1 轮计分：0.0% / 0.0% / 1.0%；15 轮：5.4% / 5.4% / 14.0%。
- **响应条件化消融**（3 个高 ASR 场景子集）：baseline 30.0% → 去掉攻击者读取历史
  下降至 **0.0% (0/36)**；防御者改成有状态（保留历史）→ 19.4%。结论：**多轮增益的
  主驱动是攻击者的响应条件化自适应，而非重复独立采样**。

**发现 4：开放竞赛暴露策略空间（§5.4）**
- 21 支攻击队 + 20 支防御队在 gpt-oss-20b 上竞赛，最终 2 轮私密计分 18,422 场；
- 固定目录式 harness（hardcode 场景专用攻击模板）在留出场景上大幅掉榜，自适应选择式
  harness（回复分类器、失败记忆、候选生成-挑选）稳步上升 → 竞赛验证了协议能捕获
  超出 baseline 采样噪声的策略发现。

**发现 5：跨场景一致性低（§5.5）**
- Kendall's W = 0.19（CI [0.02, 0.58]），14/21 场景 informative、13 个 discriminative，
  但各场景对"谁最弱"的排序不一致 → **前沿防御者的弱点不在单一轴上**。

## 四、批判性评估

### 优点（方法论贡献扎实的部分）

1. **check_success 判定可复现**：check_success 是程序化的、发布即复现（"the released
   check_success is the rubric"）。这比 judge-based 评分（GPT-4o 打分）可审计得多。
   每个候选胜场还由 4 名评审独立复核，只出现 1 例分歧。
2. **对抗代理指标的意识**（B.15 是全论文最精彩的实证）：naive substring 判定被
   自适应攻击者打爆（tickettriage 回声 67% 假胜率、smarthomejack decoy 动作），
   型字段判定免疫。这提醒所有评测者：**只要判定奖励"字符串出现"而不是"危害发生"，
   自适应攻击者就会去刷那个代理指标**。
3. **校准是实证而非直觉**：场景要过三维度 rubric + 一票否决，避免了 benchmark
   作者拍脑袋定难度的问题。
4. **诚实的边界声明**：§6 明确 memoryless 不等于生产 agent、cross-benchmark ASR 不是
   排行榜、closed-model 运行不可逐位复现。
5. **发布完整性**：场景插件、orchestrator、baseline harnesses、CLI、945 transcripts、
   重放数据集、竞赛 traces、Croissant manifest 一应俱全——复现者可以"下载即验"。

### 存疑/局限（引用或复现时要小心）

1. **N=5 的统计力量有限**：每格 15 场（3 攻击者 × 5），per-cell 二项 SE 约 ±13pp；
   只有 memleak/paperaccept/gameguru 靠 N=20 复测（B.9）钉成统计分离。其余场景的
   "gap" 只能当 suggestive。5.4% vs 5.4% 的并列是"小样本上的弱证据"，不是"两家
   一样安全"。
2. **W=0.19 的 CI 太宽**（[0.02, 0.58]），重叠 MHJ(0.204) 和 JBB(0.210)；论文只敢说
   "sits at the low end of a spectrum"，不能当"独特地不一致"引用。
3. **21 个场景是合成构造**：canary 直接放 system prompt，注入模式刻意明显；到现实
   系统的迁移未知。
4. **ablation 规模小**：消融只用 3 个高 ASR 场景、N=3（基线 N=5），且排除了 Gemini
   这一最弱防御者（API 吞吐原因）；30%→0% 的方向极强，但幅度不能外推。
5. **竞赛归因是非随机的团队观察**：固定目录 vs 自适应的涨跌来自 12 个团队的
   手写 harness 总结，harness 代码未发布，只能当案例分析。
6. **"memoryless 防御者"这个威胁模型本身有争议**：真实 agent 大多有状态，且消融
   显示有状态下 ASR 确实下降（19.4% < 30%）——所以论文测的是"单输入健壮性"，
   不是"生产安全性"。作者自己也承认 memleak 这种失败在有状态下甚至可能更糟
   （历史强化角色框架冲突 80%→100%）。

### 威胁有效性（internal validity）清单

- 攻击者能力上限：攻击者本身是 LLM，受限于模型能力与安全训练，不能替代人类红队
  （论文承认）；
- 跨 benchmark 比较的混淆：judge 类型、turn 结构、威胁面都不同（B.8 明确列出）；
- 模型快照漂移：provider 别名（claude-opus-4.6 等）会随时间重定位，transcripts +
  run_replay.log 钉住访问窗口。

## 五、可复现性评估

这篇是"评测方法"论文里可复现性**极强**的一类：

| 层面 | 可复现性 | 说明 |
|---|---|---|
| 协议（orchestrator/场景/判定） | ✅ 完全 | 代码齐发（MIT），`pip install -e ".[dev]"` + 冒烟测试 |
| 数值结果 | ✅ 发布数据可复算 | 945 transcripts 重跑 check_success 即得 ASR；W/转移矩阵/图 1–8 都能从数据重算 |
| 真实模型得分 | ⚠️ 统计对齐而非逐位 | closed-model 快照漂移 + live 攻击不可逐位复现；gpt-oss-20b 自托管层可 bit-for-bit 复跑（1,050 场噪声底） |
| 竞赛流程 | 部分 | 场景可用，团队 harness 未发布（有意为之，防双用扩散） |

**复现的正确姿势**：① 拿发布数据复算全部表格/图形（确定性）；② 用 open-weight
参考层（gpt-oss-20b + vLLM）重跑 baseline-vs-baseline；③ 要复现"前沿模型行为"则
必须重跑 live 攻击，只能对齐分布与定性结论（本文档附带的轻量复现演示了这条路径的
可行性）。

## 六、与同会话上一篇论文（ctf-abacus）的对照

| 维度 | ctf-abacus（arXiv:2608.26237v1） | Adaptive Adversaries（本篇） |
|---|---|---|
| 评测对象 | 攻击型 CTF agent | 防御型 LLM agent |
| 方法 | 事后审计 trace → solve profile / flag provenance | 事前对抗：现场生成自适应多轮攻击 |
| 数据集 | 依赖 6 模型 × 4 benchmark 的 1,435 条既有轨迹 | 自产 945 场 + 开放竞赛 18,422 场，全部发布 |
| 判定 | LLM 判官 ×2 + 人工审计 N=92，fidelity 98.3 | 程序化 check_success（型字段），人工复核 4 人 |
| 核心论点 | flag 恢复 ≠ 利用证据（62–87% 有执行证据） | 静态攻击池测不出自适应威胁（多轮 5.4–14% vs 首轮 0–1%） |
| 可复现性 | 中（框架可复现，数据不可得） | 高（代码 + 数据全发布） |

两篇互为镜像：一个验证"**结果**（flag）不等于过程（exploit）"，一个验证
"**过程**（攻击）必须适应才能暴露结果（漏洞）"。合起来构成对 LLM 安全评测的完整
批判：**分数既可能高估能力（ctf-abacus），也可能低估威胁（adaptive adversaries）。**

## 七、一句话总结

> 静态的攻击池会冻结评估对象；自适应多轮 agent-vs-agent + 每场现场再生成攻击 +
> 防代理指标的型字段判定，才能把"防御者真正的弱点"从同一个大战役里分离出来——
> 而这份工作最可贵的产出，是一套能被任何人复跑和扩展的协议，而非一组一次性数字。
