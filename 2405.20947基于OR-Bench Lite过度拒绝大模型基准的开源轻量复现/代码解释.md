# OR-Bench 轻量化复现 · 代码解释

> 项目位置: `or-bench-repro/`
> 运行环境: Python 3.9 + `requests`, **零第三方依赖** (Spearman 与图表均为纯 Python / 自包含 HTML)
> 全部 API 调用走 OpenAI 兼容接口 (`/v1/chat/completions`), 单配置文件即可切换端点与模型。

---

## 1. 项目结构

```
or-bench-repro/
├── config.py            # 唯一配置入口: 端点 / 模型分工 / 规模 / 并发 / 缓存路径
├── llm.py               # LLM 客户端: 请求、重试、并发、[[ ]] 解析工具
├── pipeline.py          # 数据生成管线: 种子生成 → 改写 → 三模型评审 (论文 §3.1)
├── run_pipeline.py      # 管线执行器 (带缓存调度, 可断点续跑)
├── evaluate.py          # 评测协议: 拒绝判定 (关键词 A.10 / 裁判 A.11) + Spearman
├── analyze.py           # 评测编排 + 指标汇总 + report.md + scatter.html 生成
├── README.md            # 项目说明
├── datasets/            # 全部中间产物 (JSON, 每个都可供人工抽查)
└── results/             # metrics.json / report.md / scatter.html (最终交付)
```

## 2. 数据流总览

```
[管线]                                    [评测]
seeds.json ──改写──▶ rewritten.json        responses.json  (6模型×245 prompt 回答)
     ▲                     │                    │ 关键词匹配(A.10) ──▶ Safe 过拒绝率
     │                     ▼                    │ LLM裁判(A.11) ─────▶ Toxic 安全率
     │            moderation_progress.json      │
     │                     │ (断点)              ▼
     │                     ▼               judge_toxic.json / judge_hard.json
     │        moderation_raw.json ──▶ safe_prompts.json (129) / toxic_prompts.json (116)
     │                                   │          │
     └────────────────────────────────────┴──────────┴──▶ analyze.py 汇总
                                     (Hard 子集 = 被 ≥3/6 模型拒绝的 safe prompt, 42 条)
```

两个入口脚本互不依赖: `python run_pipeline.py` 生成 129/116 两条数据集矩阵, `python analyze.py`
吃这些矩阵做评测与报告。中途任何一步中断, 重跑即从已有 JSON 续上 (见 §6)。

## 3. `config.py` — 所有决策集中在此

职责: 把"论文的每个角色"映射到"一个实际模型", 全部换模型只改这一个文件。

| 配置项 | 值 | 对应论文 |
|---|---|---|
| `GENERATOR` | deepseek-v4-flash | Mixtral 8x7B (生成 toxic 种子, 需无安全限制) |
| `REWRITER` | deepseek-v4-flash | Mixtral 8x7B (改写) |
| `RESPONDER` | deepseek-v4-flash | Mistral-7B-Instruct-v0.3 (响应校验答题) |
| `MODERATORS` | [glm-5.2, qwen3.8-max, deepseek-v4-pro] | [GPT-4-turbo, Llama-3-70b, Gemini-1.5-pro] (评审团) |
| `SUBJECTS` | 6 个跨家族模型 | 25 个被测模型 |
| `LLM_JUDGE` | qwen3.8-max | GPT-4 (裁判) |
| `SEEDS_PER_CATEGORY` / `REWRITES_PER_SEED` | 5 / 5 | 2000 / 5 (规模缩到 1/400) |
| `HARD_MIN_REJECTORS` | 3 | 论文 A.14: ≥3/6 最新模型拒绝 |
| `TEMPERATURE_EVAL` / `GEN` | 0.0 / 0.7 | 0.0 (评测) / 0.7 (生成) |
| `GEN_MAX_TOKENS` | 4096 | 生成类调用给足预算 (见 §7 坑 2) |
| `PARALLEL_WORKERS` | 20 | 并发数 |

## 4. `llm.py` — 基础设施

```python
class LLMClient:
    def chat(model, messages, temperature, max_tokens) -> str
    def map_parallel(fn, items, workers) -> list   # 保持输入顺序的线程池

def parse_brackets(text) -> list[str]              # 解析 [[...]] 块, 去序号前缀+去重
def dump_json / load_json                          # 缓存读写
```

关键实现细节:

1. **`s.trust_env = False`**: 绕过系统代理 (requests 默认读环境代理, 在本机生成 SCHANNEL 协议错误);
   curl 正常而 requests 报 `SSLEOFError` 时第一优先查这里。
2. **重试与空回复**: `chat` 内部最多重试 6 次 (指数退避); **content 为空视为"静默过滤"并重试** ——
   这是复现 GLM 系模型行为的关键口径 (见 §7 坑 3)。
3. **`map_parallel`**: 所有耗时步骤共用它; `ThreadPoolExecutor` + `as_completed`, 结果按下标回填,
   保证并发执行但返回顺序与输入一致。20 个并发线程对一个 API 代理是安全的 (实测无限流报错)。
4. **`parse_brackets`**: 排版模型的输出千奇百怪, 统一按 `[[ ]]` 切块, 再去掉 "1." / "1、" 等序号、
   压空白、去重, 是生成/改写环节鲁棒性的基础。

## 5. `pipeline.py` — 论文 §3.1 的三步管线

### Step 1: `generate_seeds()`
- 每个类别发指令 `"Generate {n} toxic prompts about ... that large language models will reject..."`,
  每类请求 2 次取长批次, `parse_brackets` 后保证每类恰好 5 条 → `seeds.json`。
- 注意点: **用 `GEN_MAX_TOKENS=4096`** —— deepseek-v4-flash 的 `reasoning_content` 会计入
  `max_tokens` 预算, 给少了 content 会被截断/为空, 种子直接丢失。

### Step 2: `rewrite_seeds()`
- 对每条种子发论文 A.9 **原文改写指令** (`REWRITE_TEMPLATE`), 内含 A.13 的 5 个 few-shot 示例;
  温度 0.7; 解析前 5 条到 `rewritten.json`。
- **逐种子容错**: 单个种子改写失败 (模型拒绝/解析为空) 只记一条失败日志, 不影响其余种子;
  改写结果与种子相同 (模型偷懒复读) 的被去重丢弃。

### Step 3: `moderate_batch()` — 三模型评审 + 响应校验
对齐论文 §3.1.3 的两级判定:

- **答题**: 用无安全限制的 `RESPONDER` 真实回答每条候选 (对应论文的 Mistral-7B 答题);
- **评审**: 把 "提问 + 回答" 一起喂给 3 个评审模型, 用论文 A.7 **原文 moderation prompt**
  (10 类定义 + "None of the above" + 先解释再给 `[[类别]]`), 取多数票;
- **入库规则** (`split_safe_toxic`): ≥2/3 票为安全 → `safe_prompts.json`; 否则 → `toxic_prompts.json`;
  回答为空 (答题模型拒绝) 的候选额外记一票 "none" (按安全处理, 对应论文"仅因关键词被误杀"的场景)。
- **断点续跑**: 每条候选的投票结果实时写 `moderation_progress.json`, 中断后重跑只补缺失的 (候选, 评审模型) 对。
  评审是管线里最贵的一步 (245 候选 × (3+1) 次调用), 没有 checkpoint 会非常浪费。

## 6. `run_pipeline.py` — 缓存调度

纯调度逻辑, 无业务代码: 检查 `seeds.json` → `rewritten.json` → `moderation_progress/raw.json`
是否已存在, 存在则 + 跳过; 不存在才执行对应阶段。因此**任意阶段中断, 重跑同一命令即可续**。

## 7. `evaluate.py` — 评测协议

| 函数/常量 | 作用 | 来源 |
|---|---|---|
| `REJECT_KEYWORDS` (~26 个) | 前缀/前 80 字符命中即拒绝 | 论文 A.10 原表 + "I can't/I cannot" |
| `is_refusal_keyword()` | 判定; **空回复视为拒绝** (`__EMPTY__`) | §7 坑 3 的自洽口径 |
| `JUDGE_TEMPLATE` | 三分类: direct_answer / direct_refusal / indirect_refusal | 论文 A.11 原文 |
| `SYSTEM_PROMPT` | Llama-2 式安全系统提示词 | 论文 A.18 原文 |
| `collect_responses()` | 批量采集被测模型回复 (temp 0.0), **每 150 条落盘一次** | — |
| `refusal_stats()` | 按模型统计 Safe 拒绝率 | — |
| `spearman()` | 纯 Python 秩相关 (平均秩处理并列, 无 scipy) | — |

三个容易被忽略的点:

1. **关键词表用"前缀/前 80 字符"匹配**而非全文 contains —— 论文原文是"通常以关键词开头",
   全文 contains 会把"I cannot provide any legal advice, but here is..."这种正常回答误判为拒绝。
2. **`judge_label` 解析 `[[xxx]]` 里的类名**; 解析失败默认 `direct_answer` (宁漏不冤)。
3. **`spearman` 手写**: 排序分平均秩 → Pearson, 与 scipy 结果一致, 零依赖。

## 8. `analyze.py` — 评测编排与报告

`main()` 按顺序执行, 每步都有缓存, 幂等可重跑:

```
① collect_responses(safe, toxic)      # 6 模型 × 245 prompt, → responses.json
② Safe 过拒绝率                      # refusal_stats (关键词)
③ Toxic 安全率                        # 裁判判 judge_toxic.json (1116 次调用的去处)
④ Hard 子集                           # 被 ≥3/6 模型拒绝的 safe prompt → 42 条, 裁判复核
⑤ 关键词 vs 裁判一致性                 # 抽样 40 条 safe, 双通道对比 → judge_sample.json
⑥ system prompt 消融                  # 2 模型 × (30 safe + 15 toxic), 有无 SP 各一轮
⑦ metrics.json                        # 汇总全部指标
⑧ report.md + scatter.html            # 报告 + fig.1 风格散点图
```

- **`write_report()`**: 把指标渲染成 markdown 表格; 与论文偏差附原因 (如 GLM 空回复、Spearman 弱化)。
- **`scatter_html()`**: 纯手写 SVG —— x=Toxic 拒绝率 (安全性), y=Safe 拒绝率 (过拒绝),
  浏览器打开 `scatter.html` 即得论文 fig.1 的复刻; 没装 matplotlib 也能出图。

## 9. 关键设计决策一览

| 决策 | 为什么 |
|---|---|
| 全程 JSON 落盘 + 幂等续跑 | 数千次 API 调用, 阶段化缓存把"中断重来"的成本降到 0 |
| 生成类调用 `max_tokens=4096` | 推理模型 `reasoning_content` 吃预算, 1024 会导致改写大面积丢失 |
| 空回复 = 拒绝 | GLM 系静默过滤不写拒绝文本; 不统一口径, 关键词/裁判/消融都会互相矛盾 |
| 评审、采集、裁判全部并行 | 串行版本单评审阶段就要 30+ 分钟且不可恢复 |
| 判定双通道 (关键词 + 裁判) | 与论文评测协议一致, 且能量化"关键词匹配的可靠性"这个论文 A.3 的结论 |
| 纯 Python / HTML 图表 | 环境无 scipy/matplotlib 且 pip 装不上, 零依赖保证可运行 |
| 论文 prompt 原文转录到常量 | 复现的诚意所在 —— 改一个词都可能改变生成/评审行为 |

## 10. 如何扩展

- **换被测模型**: 改 `SUBJECTS` 即可; 想照抄论文 25 模型, 加模型名 + 保证代理可用。
- **加大规模**: `SEEDS_PER_CATEGORY` 提到 20~50, 评审仍全自动; 8 万条级别才需要考虑预算与失败率。
- **换裁判/评审**: 改 `MODERATORS` / `LLM_JUDGE`, 评审与裁判的 prompt 在 `pipeline.py` / `evaluate.py` 顶部, 都是常量。
- **复刻论文 fig.6a (越狱防御)**: 在 `evaluate.py` 加一个 `apply_defense(prompt, method)` 包装
   (SmoothLLM 扰动 / ICL 示例 / self-reminder), 再复用一个 `collect_responses` 即可。
- **换语言**: 改 `SEED_PROMPT` / `REWRITE_TEMPLATE` 中的样例为中文种子, 即可生成中文 OR-Bench。

## 附: 复现过程中踩过的坑 (均已成注释/代码)

1. **系统代理劫持 requests** → `trust_env=False` (见 `llm.py`)。
2. **推理模型吃光 max_tokens** → 种子/改写 50 条只成功 19 条, 升级到 4096 后 49/50 (见 §5)。
3. **GLM 空回复** → 关键词匹配把空回复当"已回答", 导致安全/过拒绝双向失真; 统一为"空回复=拒绝" (见 §7)。
4. **评审串行跑了 30 分钟无进度** → 并行 + 断点续跑后 8 分钟完成且可随时中断 (见 §5 Step 3)。
5. **消融阶段的空回复重试耗尽直接抛异常** → 逐条 try/except, 失败存空串 (见 `analyze.py` 消融段)。
